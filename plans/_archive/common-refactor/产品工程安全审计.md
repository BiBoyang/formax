# A) 用户体验审计（终端交互为中心）

## 1) 发送普通消息 → 输出渲染（长文本/折叠/滚动/闪烁）

### 问题 A1-1：普通消息无折叠/长文控制，靠终端滚屏，易“刷屏”

* **现状**：`src/screens/REPL.tsx` 的 `renderMessage()` 直接 `Text` 输出 `msg.content`；没有行数阈值、折叠、展开交互，长输出会把输入框顶到很远，体验偏“日志流”。
* **理想体验（Claude Code）**：长回答默认折叠为摘要（可展开），工具输出也做“中间折叠”；用户可以快捷键展开/收起最后一条。
* **改动点**：

  * `src/screens/REPL.tsx`：在 `renderMessage()` 引入 `ExpandableText`（可新增 `src/components/chat/ExpandableText.tsx`）。
  * `src/utils/truncation.ts`（已存在）：复用 `truncateText()/splitLinesWithEllipsis()`，把“折叠逻辑”统一沉到 util。
* **验收标准**：

  * 发送一段 > 300 行输出：默认仅显示前 N 行 + `…(x lines hidden)`。
  * 按快捷键（例如 `Ctrl+o`）可展开/收起最后一条。

### 问题 A1-2：流式输出仍可能闪烁；虽有 buffered 模式，但缺少 UI 开关/节流策略

* **现状**：`src/features/repl/useReplController.ts` 里根据 `assistantTextMode`（`stream`/`buffered`）决定是否走 `flushAssistantBuffer()`；但“流式节流”没有做（每个 delta 触发一次渲染）。
* **理想体验**：Claude Code 默认流式但 UI 更稳（节流、合批），并且提供可见的切换入口（或 `/config`）。
* **改动点**：

  * `src/features/repl/useReplController.ts`：对 `assistantTextMode === 'stream'` 增加 50–100ms 合批更新（requestAnimationFrame/timeout）。
  * `src/screens/REPL.tsx`：增加 slash command 或快捷键切换（例如 `/config stream on|off`）。
* **验收标准**：

  * 开启 stream：输出稳定，不出现明显闪烁/跳行。
  * 切换 buffered：整段一次性显示。

# C) 安全与越权边界审计（风险清单 + 缓解）

## 高风险

### C-High-1：Bash 的“确认”由模型输入 `confirm` 控制，存在被 prompt 注入绕过的风险

* **证据**：`createBashToolHandler()` 把 `confirmed = Boolean(input.confirm || dangerouslyDisableSandbox)`，并据此执行 risky 命令。
* **风险**：插件命令或提示注入可诱导模型自动带 `confirm:true`，用户未真实确认即执行。
* **缓解**：

  * 移除/忽略模型传入的 `confirm`，改为 **工具侧强制 AskUserQuestion/ApprovalPrompt** 由用户输入产生确认 token；
  * 在 `ExecutionContext` 增加 `ctx.requireUserApproval('bash', payload)` 统一入口（可新增）。

### C-High-2：文件路径策略未做 workspace 根目录约束，Read/Write/Edit 可访问任意绝对路径

* **证据**：`ReadToolHandler` 对 `file_path` 若绝对则直接读，否则 `path.resolve(cwd, ...)`；Write/Edit 逻辑同类（Write handler 也会在 plan mode 禁止，但路径不限制）。
* **风险**：模型可读写用户家目录敏感文件（SSH key、config），属于典型越权。
* **缓解**：

  * 引入 `workspaceRoot`（默认启动时 cwd 或 git root）；
  * 新增 `resolveWorkspacePath(rawPath, cwd, root)`：拒绝 root 外路径；对绝对路径默认拒绝并提示用相对路径；
  * 对确需访问外部的场景：增加显式 `--allow-outside-workspace` 并强制二次确认。

### C-High-3：插件命令（`.claude/commands`）是“可执行提示”，存在供应链/提示注入风险

* **证据**：命令系统会把命令内容拼成 blocks 直接送入 LLM（需要在 registry 里确认实现细节；你包内确实存在插件命令加载逻辑）。
* **风险**：克隆不可信仓库后，插件命令可诱导读敏感文件、执行 Bash、开启 accept-edits。
* **缓解**：

  * 增加“仓库信任机制”：首次检测到 `.claude/commands` / `.agent/subagents` 时弹出 trust prompt，未信任则不加载或只读预览；
  * UI 中标记命令来源（builtin vs plugin）并提供 `view source`。

### C-High-4：WebFetch 可对任意 URL 发请求（潜在 SSRF / 内网探测）

* **现状证据**：WebFetch 规范化 URL 并 `fetch` 页面再交给模型分析（具体限制需看 handler；你包内确实存在 WebFetch handler）。
* **缓解**：

  * 禁止 localhost、内网 IP、link-local；
  * 默认仅允许 https；
  * 增加 allowlist/blocked list（类似 WebSearch 的 allowed_domains 设计）。

## 中风险

### C-Med-1：Console logger server 默认 listen 全网卡，可能暴露日志/内容

* **证据**：`src/utils/consoleLogger.ts` 中 `httpServer.listen(this.port)` 未指定 host（Node 默认 0.0.0.0）→ 局域网可访问（若启用）。
* **缓解**：

  * 强制绑定 `127.0.0.1`；
  * 加随机 token；
  * 默认关闭（`ENABLE_CONSOLE_LOGGER=false`）。

## 低风险 / 需要补充信息

### C-Low-1：proxy 抓包/traffic logs 默认目录是 `proxy/logs`，但包内未包含 proxy 实现

* **现状**：配置/文档提到 `FORMAX_LOGS_DIR` 默认 `proxy/logs`；但你给的 `src/**` 里未看到完整的“HTTP proxy/抓包写盘”实现。
* **结论**：**需要补充信息**（proxy 目录或相关实现）才能判断是否默认落盘敏感字段、是否脱敏。

## A) 用户体验审计（以终端交互为中心）

### 1) 发送普通消息 → 输出渲染（长文本/折叠/滚动/闪烁）

**现状**

**对标 Claude Code 的理想体验**

**验收标准**

### 1) 新增一个工具模块，需要改哪些地方？能否“只加文件不改旧代码”？

## C) 安全与越权边界审计

### 1) 插件命令（`.claude/commands/*.md`）的注入与越权风险

**风险点**

* 插件命令内容会作为 `slashEffect.kind === 'llm'` 的 `blocks` 注入用户消息里发送给模型（见 `useReplController.send()` 构造 `user` message）。
* 这意味着：插件命令本质上是“可编程 prompt 片段”。如果用户从不可信仓库复制 `.claude/commands`，会带来 prompt 注入风险（诱导调用高风险工具）。

**缓解措施（建议）**

* **给插件命令加“预览 + 二次确认”**：当 dispatch 到 `kind:'llm'` 时，先在 UI 中展示“将发送的命令内容（可折叠）”，用户确认后才真正发送。落点：`src/features/repl/useReplController.ts`（在进入 `engine.runTurn` 前插入确认）。
* 给 `createSlashCommandRegistry` 增加 `trusted: boolean`（默认 false），并在 `/help` 显示来源路径与 trust 状态。

---

### 2) Bash/Write/Edit 的“确认字段”是否可被模型绕过（高风险）

**风险点（高）**

* `Bash` handler 将 `confirmed` 视为：`input.confirm === true` **或** `dangerouslyDisableSandbox === true`，也就是**模型只要在工具输入里写 confirm:true，就能通过“需要确认”的门槛**。
* 这与 Claude Code 常见体验不一致：确认应当来自“用户交互层”，而不是模型自填。

**缓解措施**

* **P0：把“确认”从 tool input 中剥离出来**：

  * Tool input 的 `confirm` 字段只作为“模型建议”，不能直接放行；真正放行必须由 `UserInputManager` 产生的“用户确认 token / 交互结果”驱动。
  * 最小实现：当 `classifyBashCommand()` 判定需要确认时，强制走 `AskUserQuestion` 或统一 PromptDialog；用户确认后再执行。
  * 落点：`src/tools/modules/bash/handler.ts` + `src/tools/runtime/userInputManager.ts`。

### 3) 文件路径策略：避免模型猜测绝对路径；强制 cwd/白名单根目录

**现状**

* system prompt 提示“prefer paths under cwd；不确定先 Bash(pwd)”——这是**软约束**。
* 但 file tools 实际允许绝对路径：例如 `ReadToolHandler`、`GrepToolHandler` 都对 `path.isAbsolute()` 直接放行，否则 resolve(cwd)。
* `Write` 测试里甚至直接用临时目录绝对路径写文件（说明实现也接受）。

**风险点（高）**

* 只靠 prompt 很难防止模型在被注入时写到 repo 外（如 `~/.ssh/config`、`/etc/hosts`），尤其在 acceptEdits 下“免审批”。

**缓解措施**

* **P0：实现统一的路径约束函数**（例如 `resolvePathWithinCwd(cwd, inputPath)`）：

  * 默认拒绝 `..` 越界与绝对路径；
  * 若用户显式要求 repo 外路径：走 UI 二次确认（显示目标绝对路径 + 风险提示）。
  * 落点：`src/tools/executor/index.ts`（全局 policy）或 `src/tools/modules/*/handler.ts`（但更推荐集中）。

### 风险清单（高/中/低）+ 缓解措施

**高**

1. Bash 的“confirm 可由模型自填”导致越权执行高风险命令。缓解：确认必须来自 UI/用户输入（见上）。

**中**

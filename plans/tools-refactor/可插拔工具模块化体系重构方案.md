# 可插拔工具模块化体系重构方案

您好，作为资深终端产品架构师和工具系统架构师，我已仔细分析了您提供的 `manus-context.txt`、`ToolMessage.tsx` 以及 `tools-copy.json` 文件。您对工具系统模块化的目标非常清晰且符合业界最佳实践。当前 `ToolMessage.tsx` 的“一刀切”渲染方式确实是扩展瓶颈，为不同工具提供专属的定义、执行和渲染模块是必然演进方向。

## A. 工具盘点、分类与渲染方案总览

基于 `tools-copy.json` 的 18 个工具，我进行了分类，并为您规划了推荐的渲染方案和实现优先级。这张总览表是整个重构计划的蓝图。

| 工具 (Tool) | 类别 (Category) | 推荐渲染器 (Presenter) | 关键交互 (Interaction) | 优先级 | 理由 | 
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Edit** / **NotebookEdit** | 文件操作 (File Ops) | **Diff 视图** | 展开/折叠、复制 | **P0** | 核心代码修改工具，必须清晰展示变更。 |
| **Task** / **TaskOutput** | 子代理 (Sub-agent) | **带状态的折叠块** | 展开/折叠、中止 | **P0** | 异步、长时任务，需要实时状态和最终结果展示。 |
| **AskUserQuestion** | 交互 (Interactive) | **问答/表单** | 选择选项、确认/取消 | **P0** | 阻塞式交互，是 Agent 继续执行的关键。 |
| **EnterPlanMode** / **ExitPlanMode** | 规划 (Planning) | **状态切换通知** | 无 | **P0** | 明确标记 Agent 工作模式的切换，是核心心智模型。 |
| **WebSearch** | 网络 (Web) | **结构化列表** | 打开链接 (未来) | **P1** | 搜索结果需要清晰的列表展示。 |
| **Bash** / **KillShell** | 命令 (Command) | 可折叠流式日志 | 复制、滚动 | **P1** | 命令输出可能是长日志，需要流式和折叠。 |
| **Read** | 文件操作 (File Ops) | **带高亮的代码块** | 复制、滚动 | **P1** | 文件内容需要语法高亮和代码格式。 |
| **Write** | 文件操作 (File Ops) | 单行状态 | 无 | **P2** | 结果简单，通用渲染器可满足。 |
| **Glob** / **Grep** | 文件操作 (File Ops) | **文件列表/表格** | 复制路径 | **P2** | 结果是列表，通用渲染器可满足。 |
| **WebFetch** | 网络 (Web) | 单行状态 + 折叠内容 | 展开/折叠 | **P2** | 结果是摘要，通用渲染器可满足。 |
| **TodoWrite** | 规划 (Planning) | **清单 (Checklist)** | 无 | **P2** | 任务列表，可以用简单的文本列表展示。 |
| **Skill** / **SlashCommand** | 交互 (Interactive) | 单行状态 | 无 | **P2** | 调用信息简单，通用渲染器可满足。 |

## B. 各工具详解与渲染建议

以下是对每个工具的简要分析和具体的渲染建议。

### P0 - 必须优先专门渲染的工具

1.  **Edit / NotebookEdit**
    - **简介**: 对文件或 Notebook 单元进行精确的字符串替换/内容修改。
    - **输入**: `file_path`, `old_string`, `new_string` / `notebook_path`, `cell_id`, `new_source`。
    - **输出**: 纯文本确认信息。
    - **渲染建议 (推断)**: 使用类似 `git diff` 的视图。左侧为红色背景的 `- old_string`，右侧为绿色背景的 `+ new_string`。这能让用户对代码变更一目了然。`NotebookEdit` 同理。

2.  **Task / TaskOutput**
    - **简介**: 启动一个异步的、隔离的子代理来执行复杂任务 / 获取其结果。
    - **输入**: `subagent_type`, `prompt` / `task_id`。
    - **输出**: 结构化的摘要或流式日志。
    - **渲染建议 (推断)**: 一个可折叠的容器。头部显示 `[Task: general-purpose] Running...` 并带有旋转的加载动画。完成后，状态变为 `Completed` (绿色) 或 `Error` (红色)。内容默认折叠，可展开查看子代理返回的完整摘要或日志。

3.  **AskUserQuestion**
    - **简介**: 向用户提出一个或多个问题，并等待用户的选择来继续执行。
    - **输入**: `questions` 数组 (包含 `header`, `question`, `options`)。
    - **输出**: 用户选择的答案。
    - **渲染建议 (推断)**: 一个交互式表单。使用 `ink-select-input` 或类似组件，展示问题和选项。用户可以通过键盘选择，回车确认。这是阻塞式交互，UI 必须能处理这种等待状态。

4.  **EnterPlanMode / ExitPlanMode**
    - **简介**: 进入或退出“规划模式”，这是一种特殊的工作状态，Agent 会先探索、设计方案，再交由用户批准。
    - **输入**: 无 / `launchSwarm`。
    - **输出**: 状态确认信息。
    - **渲染建议 (建议)**: 这不是普通的工具消息，而是一个全局状态的切换通知。可以在 REPL 的某个固定位置（如顶部或底部状态栏）显示一个醒目的标签，例如 `[PLAN MODE]`，并在 Agent 打印“已进入规划模式”时高亮显示。

### P1 - 建议实现自定义渲染的工具

5.  **WebSearch**
    - **简介**: 执行网络搜索。
    - **输入**: `query`。
    - **输出**: 结构化的搜索结果列表。
    - **渲染建议 (推断)**: 使用有序列表渲染。每一项包含 `[1] 结果标题` 和 `(example.com)`。标题高亮，域名使用次要颜色。

6.  **Bash / KillShell**
    - **简介**: 执行 shell 命令 / 终止一个后台 shell。
    - **输入**: `command` / `shell_id`。
    - **输出**: `stdout` 和 `stderr` 的流式输出。
    - **渲染建议**: 一个可折叠的日志面板。头部显示 `Bash: git status`。内容区实时流式打印 `stdout`。如果 `stderr` 有内容，则使用红色高亮显示。

7.  **Read**
    - **简介**: 读取文件内容。
    - **输入**: `file_path`。
    - **输出**: 文件内容字符串。
    - **渲染建议**: 使用支持语法高亮的组件（如 `ink-syntax-highlight`）来渲染代码块，并显示文件名和行号。这比纯文本体验好得多。

### P2 - 可使用通用渲染器的工具

以下工具的输出相对简单，初期可继续使用或微调现有的 `ToolMessage.tsx` 作为 fallback 渲染器，后续再考虑是否需要定制。

- **Write**: 输出 `Wrote file.txt (123 bytes)`，单行状态即可。
- **Glob / Grep**: 输出是文件列表，可以用简单的多行文本展示。
- **WebFetch**: 输出是 AI 模型对网页内容的摘要，纯文本展示即可。
- **TodoWrite**: 输出是任务列表，可以用带 `[ ]` 或 `[x]` 的 Markdown 清单格式渲染。
- **Skill / SlashCommand**: 输出是简单的调用确认，单行状态即可。

## C. 工程组织结构与核心接口

这是 Plan B 的核心，我们将围绕“工具即模块”的思想组织代码。

### 0. 关键补充（更贴合当前 formax 现状）

为保证迁移过程**可控**且不破坏现有行为，建议在 Plan B 的“工具即模块”之上增加以下约束/协议（后续实现时可以逐步演进）：

1.  **ToolSpec 的事实来源（Source of Truth）**  
    - **短期（迁移期）**：继续以 `proxy/tools.json` 作为“暴露给模型的唯一事实来源”。模块优先提供 `handler/presenter`，不强制提供 `spec`。  
    - **中期（稳定后）**：允许模块对 `description/input_schema` 做运行时 patch（例如修正 `Task` schema，减少模型生成错字段）。  
    - **长期（完全模块化）**：再考虑“由模块生成/合并 `tools.json`”，消除重复维护。

2.  **Presenter 不要注入 message state**  
    不建议把 `Presenter`（React 组件引用）存进消息对象里（不利于序列化/日志/测试，也会让 state 变得不可持久化）。  
    - 消息里只存 `toolName/input/status/result/ui` 等数据；渲染时通过 `registry.getPresenter(toolName)` 决定用哪个 presenter。

3.  **执行接口需要支持进度（Progress）**  
    `execute(): Promise<ToolResult>` 对 `Bash/Task/WebFetch` 等长任务不够。建议统一为 **事件流（AsyncIterable）**：  
    - 简单工具只 yield 1 次 `result`；复杂工具可多次 yield `progress`，UI 可实时更新。

4.  **工具结果分层：给模型 vs 给 UI**  
    `tool_result.content` 是给模型的；UI 往往需要结构化数据（例如 `Edit` diff hunks、`Glob` 文件列表、`Bash` stdout/stderr 分段）。  
    - 建议 `ToolResult` 同时支持 `assistantContent`（模型可消费的字符串/简化结构）与 `ui`（presenter 专用结构化 payload）+ `artifacts`（副产物，如文件路径、统计信息）。

5.  **交互类工具需要“暂停→收集输入→继续”的协议**  
    `AskUserQuestion/EnterPlanMode/ExitPlanMode` 这类工具本质是**工作流控制**而非纯计算：  
    - 需要定义 `await_user_input`（或类似）事件，让引擎暂停、UI 收集用户选择，然后再把答案作为 `tool_result` 续回模型继续跑。

6.  **最终形态：动态生成 Tool Catalog（不再手写单份 tools.json）**  
    `tools.json` 目前是为了 **省 token/便于测试** 的子集快照；长期目标应是“以模块为源、按需生成对模型暴露的 tools 数据”：  
    - 模块提供 `spec/presenter/handler`（或仅 `handler/presenter`），由 `ToolRegistry`/`ToolSpecSource` 聚合生成 `ToolSpec[]`。  
    - 运行时可选择 profile（例如 `min`/`full`）：`min` 缩短 description、减少 tool 数；`full` 对齐 `tools-copy.json` 的全集能力。  
    - 允许“导出一份生成后的 tools.json”用于抓包对比/调试，但它不再是唯一维护入口。

### 2. 核心 TypeScript 接口签名

这些接口定义了每个工具模块必须遵守的契约。

```typescript
// src/tools/types.ts

import type { JSONSchema4 } from 'json-schema';
import type { FC } from 'react';

/**
 * 暴露给 LLM 的工具定义
 * - 迁移期：默认来自 proxy/tools.json（事实来源）
 * - 稳定后：允许被模块/运行时做 patch
 */
export interface ToolSpec {
  name: string;
  description: string;
  input_schema: JSONSchema4;
}

/** ToolSpec 来源（迁移期默认 proxy/tools.json） */
export interface ToolSpecSource {
  listSpecs(): Promise<ToolSpec[]>;
}

export type ToolExecutionEvent =
  | { type: 'progress'; tool_use_id: string; ui?: any; message?: string }
  | { type: 'await_user_input'; tool_use_id: string; ui: any } // AskUserQuestion 等
  | { type: 'result'; result: ToolResult };

/**
 * 工具执行的结果
 */
export interface ToolResult {
  tool_use_id: string;
  /** 发送给模型的 tool_result 内容（尽量稳定、可压缩） */
  assistantContent: string;
  /** 给 presenter 的结构化 payload（diff/list/sections/metrics 等） */
  ui?: any;
  is_error?: boolean;
  artifacts?: any; // 附加产物，如文件路径、统计信息、可点击引用等
}

/**
 * 工具执行器的接口
 */
export interface ToolHandler {
  /** 
   * 执行工具的核心逻辑
   * @param toolCall - 模型生成的工具调用请求
   * @param context - 执行上下文，包含 cwd, signal 等
   * @returns 事件流（支持 progress / await_user_input / result）
   */
  execute(toolCall: any, context: { cwd: string; signal: AbortSignal }): AsyncIterable<ToolExecutionEvent>;
}

/**
 * 工具渲染器的 Props
 */
export interface ToolPresenterProps {
  toolCall: any; // 工具调用的输入参数（用于展示 params）
  toolResult?: ToolResult; // 工具执行的最终结果（含 ui/artifacts）
  status: 'running' | 'completed' | 'error';
}

/**
 * 工具渲染器的接口 (React Component)
 */
export type ToolPresenter = FC<ToolPresenterProps>;

/**
 * 一个完整的工具模块定义
 */
export interface ToolModule {
  /** Tool name，用于 registry 路由 */
  name: string;
  /** 可选：工具别名（用于兼容 Claude Code / 历史命名） */
  aliases?: string[];
  /** 可选：模块提供 spec（仅用于新增工具或运行时覆盖） */
  spec?: ToolSpec;
  handler: ToolHandler;
  presenter: ToolPresenter;
}
```

### 3. `ToolRegistry` 与调用流程

`ToolRegistry` 是连接所有模块的枢纽。

```typescript
// src/tools/registry.ts

import { FallbackToolPresenter } from './fallback/FallbackToolPresenter';

export class ToolRegistry {
  private handlers = new Map<string, ToolHandler>();
  private presenters = new Map<string, ToolPresenter>();
  private specs = new Map<string, ToolSpec>();
  private aliases = new Map<string, string>();
  private patches: Array<(specs: ToolSpec[]) => ToolSpec[]> = [];
  constructor(private specSource: ToolSpecSource) {}

  // 在应用启动时，加载所有工具模块
  async loadModules() {
    // 伪代码: 遍历 src/tools/modules/*
    // for each module directory:
    //   const handler = await import('./modules/Read/Read.handler');
    //   const presenter = await import('./modules/Read/Read.presenter');
    //   this.register({ handler: handler.default, presenter: presenter.default, spec: spec?.default });
  }

  register(module: ToolModule) {
    this.handlers.set(module.name, module.handler);
    this.presenters.set(module.name, module.presenter);
    if (module.spec) this.specs.set(module.name, module.spec);
    for (const alias of module.aliases ?? []) this.aliases.set(alias, module.name);
  }

  resolveName(toolName: string): string {
    return this.aliases.get(toolName) ?? toolName;
  }

  getHandler(toolName: string): ToolHandler | undefined {
    return this.handlers.get(this.resolveName(toolName));
  }

  getPresenter(toolName: string): ToolPresenter {
    return this.presenters.get(this.resolveName(toolName)) || FallbackToolPresenter;
  }

  /** 运行时 patch：依赖 subagents/featureFlags 等动态信息 */
  addPatch(fn: (specs: ToolSpec[]) => ToolSpec[]): void {
    this.patches.push(fn);
  }
  
  async listSpecs(): Promise<ToolSpec[]> {
    // 迁移期：优先来自 proxy/tools.json（specSource），再叠加/覆盖模块 spec
    const base = await this.specSource.listSpecs();
    const merged = new Map(base.map((s) => [s.name, s]));
    for (const [name, spec] of this.specs) merged.set(name, spec);
    let specs = Array.from(merged.values());
    for (const patch of this.patches) specs = patch(specs);
    return specs;
  }
}
```

### 4. 运行时协议补齐（可直接用于编码）

#### 4.1 单个工具调用的状态机（tool_use → tool_result）

```
Idle
  -> tool_use received
  -> running
      -> progress* (0..n)
      -> await_user_input? (0..1)   // AskUserQuestion 等交互工具
  -> completed | error | aborted
  -> tool_result sent to model
  -> Idle
```

分层归属建议：
- Engine：只负责 “LLM loop + tool_result 回灌”（保持你现在的 `ChatEngine` 结构）
- Controller：维护 toolRuns / expanded / focus / abort controllers（UI state）
- UI：渲染 + 收集用户输入（交互工具）
- ToolModule：只做 handler/presenter/spec override（不做 orchestration）

#### 4.2 取消语义（两层取消，避免概念混乱）

- **Stop waiting（中止本次 tool call 等待）**：终止 “这轮对 tool 的等待”，返回 `Request aborted` 或类似错误；对应 `AbortSignal`。  
- **Cancel task（真正停止后台任务）**：停止后台 bash/子代理任务本身；可能需要 `KillShell(shell_id)` 或 `TaskManager.cancel(task_id)`（best-effort）。

建议在 UI 上显式区分按钮/快捷键：
- running + block=true：`[s] Stop waiting`
- running + cancellable：`[c] Cancel task`

#### 4.3 Task/TaskOutput（建议引入 TaskManager）

只要支持 `Task(run_in_background=true)`，就需要一个统一的任务管理层（否则 TaskOutput 没有可靠数据源）。

```ts
export type TaskState = 'queued' | 'running' | 'completed' | 'error' | 'cancelled'

export type TaskRecord = {
  taskId: string
  type: 'bash' | 'subagent' | 'remote'
  state: TaskState
  createdAt: number
  startedAt?: number
  finishedAt?: number
  // 可选：增量日志（用于 TaskOutput UI）
  stdoutTail?: string[]
  stderrTail?: string[]
  exitCode?: number
  errorMessage?: string
  abort?: () => void
}

export interface TaskManager {
  create(record: Omit<TaskRecord, 'state' | 'createdAt'>): TaskRecord
  get(taskId: string): TaskRecord | undefined
  list(): TaskRecord[]
  wait(taskId: string, opts: { timeoutMs: number }): Promise<TaskRecord>
  cancel(taskId: string): Promise<boolean> // best-effort
}
```

`TaskOutput` presenter 推荐吃结构化 `ui` payload（避免解析字符串）：

```ts
export interface TaskOutputUI {
  kind: 'task_output'
  taskId: string
  state: TaskState
  startedAt?: number
  finishedAt?: number
  progress?: { current?: number; total?: number; percent?: number; label?: string }
  stdout?: { head?: string[]; tail?: string[]; totalLines?: number; truncated?: boolean }
  stderr?: { tail?: string[]; totalLines?: number; truncated?: boolean }
  exitCode?: number
  errorMessage?: string
  cancellable?: boolean
  cancelHint?: 'KillShell' | 'AbortAgent' | 'Unknown'
}
```

#### 4.4 AskUserQuestion（await_user_input 协议）

交互类工具不要“伪装成一次性 Promise”，而是显式暂停引擎：
- handler 产出 `await_user_input` 事件（带 questions/options payload）
- UI 渲染选择器，收集答案
- Controller 把答案回填为 `tool_result` 再继续 Engine loop

建议回填给模型的 `assistantContent` 使用稳定 JSON（方便模型消费，且易裁剪）：

```json
{ "answers": [ { "header": "Auth", "selected": ["date-fns"], "other": null } ] }
```

#### 4.5 assistantContent 裁剪规则（防止上下文爆炸）

强约束：
- `assistantContent`：summary-first，建议上限 1–2KB（统计 + topN + truncated 标记）
- 大内容进入 `ui` 或落盘（日志文件），并在 `assistantContent` 明确提示 “truncated，可再次调用获取更多/分页”

#### 4.6 UI Kit / Keymap / Focus（避免你之前遇到的空格与宽字符问题）

- 不要靠拼空格对齐；尽量用 Ink `<Box>` 做布局，必要时用 `string-width` 测宽。
- 折叠交互统一（例如 `ctrl+o`），并做集中 `Keymap` 管理：
  - 输入框聚焦时屏蔽全局快捷键（只保留 `esc/enter`），避免抢键与 IME 冲突。
- 为 P0 presenter（TaskOutput/AskUserQuestion/Edit）增加 “交互快照测试/按键测试”，防止回归。

## D. 增量迁移计划

### 0. 验收与回滚策略（建议提前约定）

- Feature flag：`TOOL_UI_MODE=legacy|modular`（默认 legacy，逐步切换）
- 单工具禁用：`TOOL_UI_DISABLE=TaskOutput,AskUserQuestion`（presenter 崩溃时可快速降级）
- Presenter crash fallback：渲染异常自动 fallback 到 `FallbackToolPresenter`（并在 footer 提示 “fallback applied”）

1.  **阶段 0: 搭建基础框架 (1-2 天)**
    - 创建 `src/tools` 目录结构、`types.ts` 接口定义、`registry.ts` 和 `fallback/FallbackToolPresenter.tsx`。
    - `FallbackToolPresenter` 的实现可以直接从您现有的 `ToolMessage.tsx` 迁移过来。
    - 修改 `cli.tsx` 或应用入口，实例化 `ToolRegistry` 并加载。
    - **验收标准**: 应用能正常运行，所有工具都通过 `FallbackToolPresenter` 渲染，表现应与重构前完全一致。

2.  **阶段 1: 迁移现有工具 (2-3 天)**
    - 将您已实现的 `Read`, `Write`, `Bash`, `Glob`, `Grep`, `Edit`, `Task` 逻辑从 `LocalToolHandler` 和其他地方剥离出来，创建对应的 `src/tools/modules/{ToolName}/` 目录和 `*.spec.ts`, `*.handler.ts` 文件。
    - 暂时让它们都使用 `FallbackToolPresenter`。
    - **验收标准**: 所有现有工具的功能正常，但代码结构已经迁移到新模块中。

3.  **阶段 2: 实现 P0 级自定义渲染器 (3-5 天)**
    - 集中精力为 `Edit`, `Task`, `AskUserQuestion`, `EnterPlanMode` 创建专属的 `*.presenter.tsx`。
    - 这是价值最高的投入，能立刻带来质的体验提升。
    - **验收标准**: `Edit` 显示为 diff 视图，`Task` 显示为带状态的折叠块，`AskUserQuestion` 弹出交互式表单。

4.  **阶段 3: 逐步覆盖 P1/P2 工具 (持续迭代)**
    - 根据优先级和资源，逐步为 `WebSearch`, `Bash`, `Read` 等工具创建更美观的渲染器。
    - 同时，开始实现 `tools-copy.json` 中尚未支持的工具（如 `NotebookEdit`, `WebFetch` 等），直接在新框架下创建它们的完整模块。
    - **验收标准**: 新工具被不断添加，且拥有自己的专属 UI，`FallbackToolPresenter` 的使用场景越来越少。

### 4. 风险与对策（建议在编码前定下来）

1. 循环依赖（Task/SubAgent/Executor/Engine）→ 用接口抽象 + 延迟注入（避免 handler import engine 实例）
2. 上下文爆炸（tool_result 过长）→ 强制 `assistantContent` 上限 + 大内容只进 `ui`/落盘
3. 交互/快捷键冲突（AskUserQuestion/输入框/IME）→ Keymap + Focus 管理 + 按键测试

通过以上四个阶段，您可以在不影响现有功能的前提下，平滑地将项目重构为一个高度模块化、可扩展的工具系统，为未来集成更多、更复杂的工具打下坚实的基础。

由于 Claude Code 并非开源项目，我无法确定其内部的真实渲染实现。本方案中所有标注为"推断"或"建议"的渲染方案，均基于以下来源：

## G. 参考实现（Kode-cli，可选）

您提到的 `Kode-cli` 项目在工具层的组织方式与本方案高度一致，可作为“落地实现”的强参考：

1.  **目录层级**：`src/tools/<ToolName>Tool/`，每个工具目录内通常包含：  
    - `<Tool>.tsx`：工具实现（包含执行 + 专属 UI 渲染）  
    - `prompt.ts`：工具/子流程的提示词  
    - `utils.ts`/子组件：例如 `BashToolResultMessage.tsx`、diff 组件等

2.  **接口映射**（对照本方案的关键点）：  
    - `call()` 采用 `AsyncGenerator`（天然支持 progress）→ 对应本方案的 `ToolExecutionEvent`  
    - `renderResultForAssistant()`（给模型）与 `renderToolResultMessage()`（给 UI）分离 → 对应本方案的 `assistantContent` vs `ui`

3.  **终端排版细节**：Kode 中大量使用不可断空格（如 `&nbsp;`）来控制缩进/对齐；这也解释了为什么 `⏺` 后的空格在某些渲染/复制场景会出现“看起来多一个空格”的现象。迁移 presenter 时建议统一用“组件布局 + 最少字符串空格”的方式稳定输出。
